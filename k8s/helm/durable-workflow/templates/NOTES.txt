Durable Workflow {{ .Chart.AppVersion }} (chart {{ .Chart.Version }}) was installed

{{- if include "durable-workflow.isNative" . }}
What just happened
------------------
This release runs the native Server (runtime=native). Each pod is one process
that serves the API, checks its database schema at startup and runs timers,
repair, retention and schedules itself. There is no worker Deployment,
scheduler CronJob, migration Job or Redis.
{{- if .Values.server.enabled }}

The API Deployment "{{ include "durable-workflow.serverDeploymentName" . }}"
{{- if .Values.server.autoscaling.enabled }} scales between {{ .Values.server.autoscaling.minReplicas }} and {{ .Values.server.autoscaling.maxReplicas }} replicas
{{- else }} runs {{ .Values.server.replicaCount }} replicas
{{- end }} behind the Service
"{{ include "durable-workflow.serverDeploymentName" . }}" on port {{ .Values.server.service.port }}.
{{- end }}

Each pod holds up to four database connections. A newer native release with a
schema change needs the explicit schema upgrade in the chart's UPGRADING.md:
stop every Server, back up the database, then upgrade with
native.schemaUpgrade.enabled=true.
{{- if not (get (default (dict) (get (default (dict) .Values.native) "storage")) "existingClaim") }}

External payload objects are stored in an emptyDir and are lost when a pod is
replaced. Before a namespace enables external payload storage, set
native.storage.existingClaim (ReadWriteMany when more than one replica runs).
{{- end }}
