# October 27, the parity reference moves to published 2.11.5

- **Before.** The Shared Server fixtures compared native and embedded
  against published Server 2.11.4 (Core 2.14.2), with two SQLite
  workarounds: `update-validation` and `service-calls` recorded apart from
  the main corpus, with PHP's maintenance loop stopped (#723, #796).
- **Reference.** Published Server 2.11.5, Core 2.15.1, as General verified
  it (release run 40478372197):
  - source `721b2831975cc898cc39d7528c5ba7e8441fe744`;
  - index `sha256:f4f2ec64a6522ee18a31542a30554873dbaa2f5d3af3ccb52deb914591699c20`,
    identical on Docker Hub and GHCR;
  - linux/amd64 `sha256:bcc672859a399d1df234fc304531ab06b7bfa8acad7cb2c9da95f8e7ab5c98b4`;
  - linux/arm64 `sha256:3160f4f58ab9b144705c3e4d5d97b0881b0891c1f00e9ab6b99b3245a8c3b26a`.

  `tests/Fixtures/ServerParityBaselines/php-2.11.5.json` records it. The SDK,
  CLI, Waterline and sample-app pins are unchanged. The takeover cohorts are
  not affected: each names its own source release and layout.
- **The SQLite maintenance pause is gone.** 2.11.5 carries the
  update-validation lock fixes (#726) and atomic service admission (#796).
  Cloud's installed #726 acceptance passed 15 of 15 original SQLite
  records with the maintenance loop running, and General's #796 check
  passed 10 of 10. So the SQLite job records both fixtures in its main
  corpus, with the loop running, as the MySQL and PostgreSQL jobs always
  have. `update-validation-sqlite.sh`, `php-maintenance-window.sh` and their
  tests are removed. The native image corpus does the same.
- **Expectation changes**, all 2.11.5 behavior:
  - `service-calls`: the "replay other caller" step returns. An idempotency
    key belongs to the operation (Workflow #931): another caller namespace
    reusing it gets `403 service_operation_forbidden`, and no call or audit
    row is written. 91 requests.
  - `repair-pass`: the report adds Core 2.15's linked service-call counts
    (`service_call_linked_candidates`, `service_call_links_reconciled`,
    `service_call_linked_failures`).
  - `bridge-adapters`: a second bounded answer for the #777 foreign-instance
    defect. Core 2.15.1 checks the namespace first, but 2.11.5's bridge
    controller still echoes "cannot be reused with a different namespace"
    for both foreign starts. Server #811 (merged after 2.11.5) answers the
    intended "is unavailable". The intended answer is unchanged.
- **Native.**
  - Refuses an idempotency-key replay from anyone but the call's owner,
    matching Core 2.15.1's `ServiceCallIdempotency` and 2.11.5's 403.
  - The repair report adds the three linked counts as zeros. Native binds no
    call to a workflow run: workflow-bound handlers answer 501 (#794).
  - Takeover now refuses a PHP database holding an open call bound to a
    workflow run (`upgrade_source_service_calls_workflow_bound_open`), which
    PHP closes when its run ends and native never would. The service-call
    inspection reports the count as `workflow_bound_open`. Closed
    workflow-bound calls and open calls of other bindings still take over.
- **Checked** (local SQLite, `native-image-corpus.sh` with a native image
  built from this branch, published 2.11.5 and embedded 2.11.5):
  - first run: native and embedded passed all 73 cases; 2.11.5 passed 71,
    including `update-validation` and `service-calls` with the maintenance
    loop running. It failed `repair-pass` (the three new counts) and
    `bridge-adapters` (`start_other_type`), the two changes above;
  - after them, both fixtures pass against the running 2.11.5 server;
  - second full run, native image rebuilt with them (runner revision
    `73d43c8c`, the same tree): published 2.11.5, native and embedded each
    pass all 73 cases, and the three records compare equal;
  - native: `cargo test --lib` for repair_pass, waterline_import and the
    upgrade module (60 tests) pass, and the service-calls execution tests
    pass 8/8 on SQLite. CI runs them on all four databases.
