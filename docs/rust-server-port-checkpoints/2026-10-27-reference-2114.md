# October 27, the parity reference moves to published 2.11.4

- **Before.** The Shared Server fixtures compared native and embedded
  against published Server 2.11.1 (Workflow 2.10.2).
- **Reference.** Published Server 2.11.4, Core 2.14.2, as General and
  Security verified it:
  - source `ad3ac5fda0a30a58084b2d68569f2d91e23fabf3`;
  - linux/amd64 `sha256:bee30cde5b70a429561a49f25daf4ef71a1e405d43322f78ff1b8137029c80f3`;
  - linux/arm64 `sha256:cc297aa7d1f81b8bfa1169de6980dabe58d9776dcf513f379dcba2a51b1f5cc7`.

  `tests/Fixtures/ServerParityBaselines/php-2.11.4.json` records it. The SDK,
  CLI, Waterline and sample-app pins are unchanged. 2.11.4 has no schema
  change from 2.11.3, so the existing-PHP takeover cohorts expect the
  `php-2.11.3` layout. Its API route table is the same as 2.11.1's, so the
  route inventory still holds.
- **Expectation changes**, all Core 2.14 behavior:
  - `repair-pass`: the report adds the dispatch-outbox counts
    (`service_call_dispatch_candidates`, `service_call_dispatches_enqueued`,
    `service_call_dispatch_failures`).
  - `service-calls`:
    - an execute request's `wait_timeout_seconds` is bounded at 60;
    - handler metadata names `service_call_idempotency_key` (null for a call
      dispatched when it is accepted).
- **Native.**
  - The repair report adds the three counts as zeros: native runs a call's
    handler when it accepts the call, so it has no outbox.
  - The execute bound is 60.
  - Handler metadata carries the null key.
  - Task-queue views report published 2.11.3's `poll_transport` as
    `unavailable`, since native records no early poll disconnects. Every poll
    returns the ordinary JSON response, declining the opt-in progress
    transport; SDKs must accept both.
- **Boundary: Workflow #931.** `service-calls` no longer repeats an
  idempotency key from another caller namespace.
  - Published 2.11.1 created a separate call for that caller.
  - 2.11.3 and 2.11.4 replay the first call and rebind its handler identity.
  - The prepared correction refuses the foreign caller.

  Recorded against 2.11.4, that step and the three that follow from it were
  the only differences in the whole selection. The step returns, with the
  corrected answer for native too, once a release carries the correction.
  Until then native keeps 2.11.1's separate call.
- **Checked.**
  - CI's fixture selection (the corpus without `update-validation`) recorded
    on SQLite against published 2.11.4. Before the boundary, only
    `service-calls` differed.
  - After it, `repair-pass`, `service-calls` and `storage-test` pass against
    both 2.11.4 and native from this branch, and the two records compare
    equal.
  - The service-calls contract test passes 22/22. CI runs the full selection
    on all four databases.
