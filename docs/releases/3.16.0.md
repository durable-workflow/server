# Durable Workflow Server 3.16.0 (native)

Server 3.16.0 bounds native's periodic maintenance scans by open work instead
of retained history. Its immutable images are `durableworkflow/server:3.16.0`
and `ghcr.io/durable-workflow/server:3.16.0`; the published Compose default
selects 3.16.0. Rolling aliases move separately after published-image
qualification.

**Upgrade:** this release requires an explicit additive `schema-upgrade` from
3.15.x (or 3.14.x) on every backend; see [Upgrade and rollback](#upgrade-and-rollback).
After the schema step, rolling back to 3.15.x requires restoring the
pre-upgrade backup: a 3.15.x binary refuses the upgraded database with
`native_schema_newer_than_binary`. Worker protocol and control-plane versions
are unchanged.

## Maintenance scans bounded by open work

Native's scheduler tick (every 250 ms), repair pass (every 5 s) and retention
pass (every 60 s) select runs and activity executions by open status, and
retention takes a namespace's run summaries in close order. No index served
those reads, so every pass read every retained run, and idle CPU and I/O grew
with retained history rather than with open work. The schema step adds three
native-only indexes that these scans now seek:

| Index | Columns | Scans it serves |
| --- | --- | --- |
| `dw_workflow_runs_status_deadline` | `workflow_runs (status, cancellation_deadline_at)` | timeout cleanup, due activities and cooperative deadlines (250 ms); repair of expired run deadlines (5 s) |
| `dw_activity_executions_status` | `activity_executions (status)` | due activities (250 ms); repair of expired activities and `GET /api/system/activity-timeouts` (5 s) |
| `dw_workflow_run_summaries_retention` | `workflow_run_summaries (namespace, closed_at, id)` | retention candidates (60 s) |

Query text and results are unchanged. On a 1 vCPU / 1 GiB native Dev cell
(MySQL 8.0, no workers or clients connected), idle CPU with 100,000 retained
runs dropped from 38.8% on 3.15.0 to 3.3%; at 10,000 retained runs it dropped
from 15.2% to 1.6%. The slowest scan at 100,000 runs, timeout cleanup, went from
about 3.5 s to 0.015 ms. The other periodic queries (activity leases, timers,
schedules, task repair and service-call deadlines) already sought an index
(#1256, #1258).

## Upgrade and rollback

This release requires an explicit additive schema upgrade from 3.15.x on every
backend:

| Backend | Schema step |
| --- | --- |
| SQLite | 16 → 17 |
| PostgreSQL | 17 → 18 |
| MariaDB | 17 → 18 |
| MySQL | 18 → 19 |

Each step creates the three indexes above. It rewrites no existing rows. The
procedure is the same as for 3.14.0:

1. Stop every Server replica sharing the database, including replicas outside
   this deployment. Keep the database running.
2. Back up the database and every external-payload root.
3. Select the new immutable image and run that image's `schema-upgrade` once.
4. Start every replica on the same 3.16.0 image and verify readiness, reported
   version 3.16.0 and worker registration.

Startup does not upgrade an older schema automatically and refuses to serve it
(`native_schema_upgrade_required`). From 3.13.x or earlier, the same command
also applies the intervening steps described in the
[3.14.0 upgrade notes](3.14.0.md#upgrade-and-rollback) and the
[3.12.0 upgrade notes](3.12.0.md#upgrade-and-rollback).

Do not create these indexes by hand ahead of the upgrade. A same-named index
that the step did not create is refused rather than adopted, and the upgrade
stops.

### How long the step takes

Index build time grows with retained runs, roughly 30 seconds per million
retained runs. Measured at 1,000,000 retained runs on 2 CPUs:

| Backend | Build time | How it builds |
| --- | --- | --- |
| MySQL 8.0 | about 25 s | Online (in-place InnoDB build); writes are not blocked |
| MariaDB 10.11 | about 20 s | Online (in-place InnoDB build); writes are not blocked |
| PostgreSQL 17 | about 5 s | One transaction; writes to the indexed tables wait until it commits, reads are unaffected |

Very small cells are slower per row: the 1 vCPU Dev cell took 11.8 s for MySQL
18 → 19 at 100,000 retained runs. The step still runs with every Server replica
stopped, as `schema-upgrade` requires; the online builds matter only to other
clients of the same database server.

### If the step is interrupted

Re-run `schema-upgrade`; it resumes. SQLite and PostgreSQL apply their step in
one transaction, so an interrupted step leaves the previous schema in place.
MySQL and MariaDB resume from whichever indexes were already committed.

On MySQL, if the `schema-upgrade` client died while an index was building, the
database server keeps running that `CREATE INDEX` and its session keeps holding
the upgrade lock. Wait for the build to finish, or find it in
`SHOW PROCESSLIST` and `KILL` it, before re-running. Otherwise the re-run waits
60 seconds for the lock and refuses with `native_initialization_busy`.

### Takeover of a PHP-schema database

[Takeover](../rust-server-upgrade-takeover.md) of a PHP Server 2.x database
with 3.16.0 now builds these three indexes too, so its duration grows with
retained runs in the same way.

### Compose

For a single-node Compose deployment, stop Server while leaving MySQL running,
back up MySQL and `server_storage`, set `DW_SERVER_IMAGE` to the 3.16.0 image,
then pull and upgrade once:

```bash
docker compose --env-file durable-workflow.prod.env \
  -f docker-compose.published.yml stop server
docker compose --env-file durable-workflow.prod.env \
  -f docker-compose.published.yml pull server
docker compose --env-file durable-workflow.prod.env \
  -f docker-compose.published.yml run --rm --no-deps server schema-upgrade
docker compose --env-file durable-workflow.prod.env \
  -f docker-compose.published.yml up -d --wait
```

From 3.15.x on MySQL, the upgrade reports `from_schema_version:18`,
`schema_version:19`, `status:upgraded`; a repeat reports `status:current`.
Then verify `/api/ready`, `/api/cluster/info` version `3.16.0`, and worker
registration.

### Helm

With Helm, run the 3.16.0 image's `schema-upgrade` through the opt-in
`native.schemaUpgrade.enabled` hook or the manual Job described in the chart's
native schema upgrade section, after scaling every Server replica to zero. The
chart that selects 3.16.0 by default is published separately; follow its
versioned upgrade notes, and make any explicit `image.tag` or `image.digest`
override select the intended image. For a large MySQL database, raise
`helm upgrade --timeout` above the 10 minutes in the chart's universal
procedure; the hook Job itself allows 1800 seconds.

### Rollback

Until `schema-upgrade` has run, going back to 3.15.x is an ordinary image
rollback. After it, rolling back requires restoring the pre-upgrade database
and payload-storage backup. A 3.15.x binary does not ignore the new indexes: it
refuses the upgraded database with `native_schema_newer_than_binary` and does
not start, so do not try to run one against it. Workflows and objects recorded
after the upgrade are not in that backup and are lost. Do not run 3.15.x and
3.16.0 replicas against one database.

## Unchanged

Worker protocol `1.20`, control-plane version `2`, codec and command shapes,
the HTTP API and the public external-payload reference shape are unchanged.
There are no new capabilities. The PHP Server remains 2.11.8, retired and
unpatched; see the
[retirement/security notice](../security/retired-php-server-2026-11-13.md).
