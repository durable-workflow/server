# Durable Workflow Server 3.31.1 (native)

This release keeps the 3.30.0 database schema on every backend. No schema
upgrade is required from 3.30.0.

## Security

- Patched Debian `libpam0g`, `libpam-runtime`, `libpam-modules`, and
  `libpam-modules-bin` to `1.5.2-6+deb12u3` in the native runtime image for
  CVE-2025-6020 (HIGH), which blocked promotion of `3.31.0`.

## Activity workflow continuation v2

Native Server implements and advertises activity workflow continuation v2
([#1181](https://github.com/durable-workflow/server/issues/1181), #1353, #1356,
#1359, #1360, #1362). The contract lives in
[`docs/contracts/activity-workflow-continuation-v2.md`](../contracts/activity-workflow-continuation-v2.md).

`server_capabilities.activity_workflow_continuation` keeps every v1 field and
`version: 1` for released SDKs and adds `supported_versions: [1, 2]` and a
`v2` descriptor (`complete_endpoint`, `supported_commands`, `max_commands`,
`requires_worker_capabilities`, `tail_max_events`, `tail_max_bytes`).

- Workflow task completion accepts an optional `continuation_tail: {"version": 2}`
  alongside a `sticky_cache` claim with `history_last_sequence`. When set, the
  completion returns the appended events after the worker's boundary (bounded by
  the tail event and byte budgets) and restricts a carried `activity_poll` to
  activity tasks created by that completion.
- `POST /api/worker/activity-tasks/{taskId}/continuation/complete` accepts
  `continuation.version: 2`. In one write transaction under the transition lock,
  Server checks the receipt, proves the cached prefix in O(1) without reading a
  history page, appends `ActivityCompleted`, applies the nested workflow
  completion and optional carried `activity_poll`, and returns the new tail.
- Twelve explicit decline reasons fall back via a savepoint to the ordinary
  activity completion and carried `workflow_poll` without an extra round trip.
- Continuations stay off by default in every SDK until the published-artifact
  qualification benchmark in #1181 passes.

## Parallel group policies

Native Server admits, records, and routes explicit parallel group policies
([.github #232](https://github.com/durable-workflow/.github/issues/232), #1376,
#1381, #1383, #1384).

- Workflow tasks can open parallel groups with explicit `propagate` or `settle`
  policies. `settle` groups wake the workflow once every member has an outcome.
- Server routes runs with explicit parallel group policies only to workers that
  advertise those policies, including workflow, query, and update-validation
  tasks.

## Database pool and held-poll bounds

- Held-poll probes, admission, readiness, claims, and maintenance stay off the
  last database pool slot, and later probes wait for a read slot within the
  poll's own deadline (#1348, #1358, #1380).
- Pre-checkout pings, transition queue waits, in-flight statements, pool
  releases, large database writes, and shutdowns are bounded against silent or
  non-reading database peers (#1358, #1375, #1387).

## Other fixes

- Receipt-ordered condition groups now wake when their timeout timers fire
  (#1386).
- Native run lists can opt in to include the recorded timeout-cleanup outcome
  without per-row lookups (#1379).
- Reading history for a pruned run now answers with an empty final page instead
  of HTTP 413 (#1369).
- Export manifests now mark native external references as documented (#1370).
- Retention policy plans describe stored revision timestamps at their exact
  stored precision (#1364).
- Updated locked Symfony 7.4 packages in the legacy PHP tree for upstream
  security advisories (#1357).

## Upgrade from 3.30.0

Database schema versions are unchanged from 3.30.0 (SQLite 20, PostgreSQL 21,
MySQL 23, MariaDB 22). Upgrading from 3.29.0 or earlier still requires the
stopped-node `schema-upgrade` documented in the
[3.30.0 release notes](3.30.0.md#upgrade-from-3290).

The worker protocol version stays 1.20. The published Compose file defaults to
3.31.1.
