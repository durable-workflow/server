# Durable Workflow Server 3.5.0 (native)

Server 3.5.0 fixes updates for runs started before their worker registered,
adds sticky execution with history suffixes, and prunes expired runs from the
maintenance loop. Its exact images are `durableworkflow/server:3.5.0` and
`ghcr.io/durable-workflow/server:3.5.0`; the published Compose default selects
3.5.0. Rolling aliases move separately after published-image qualification.

## Upgrade

**Schema upgrade required.** This release adds one native-only table,
`dw_run_command_contracts`. The native schema moves from 11 to 12 on MySQL,
MariaDB and PostgreSQL, and from 10 to 11 on SQLite.

A server never upgrades its schema at startup. Started on the earlier schema,
3.5.0 refuses with `native_schema_upgrade_required`. To upgrade:

1. Stop every native node.
2. Back up the database.
3. Run the 3.5.0 image's `schema-upgrade` once, with the same `DB_*`
   settings, as described in
   [Native schema upgrades](../../rust/README.md#native-schema-upgrades).
   With the Helm chart, set `native.schemaUpgrade.enabled=true` for the
   `helm upgrade`.
4. Start the 3.5.0 nodes.

The upgrade only creates the new table and its index; it rewrites no rows.
On MySQL and MariaDB an interrupted upgrade resumes when you run
`schema-upgrade` again. Databases from 3.0.x through 3.4.x are upgraded by the
same command.

**Rolling back to 3.4.x requires restoring the backup.** Once a database is on
the new schema, a 3.4.x server refuses it with `native_schema_newer_than_binary`.
To go back, restore the backup taken before the upgrade.

The worker protocol stays at `1.20` and the control plane at version `2`.

## Updates for runs started before their worker registered

A run started before any worker on its queue registered its command contract
used to reject every update for the rest of the run as
`rejected_unknown_update` ([#962](https://github.com/durable-workflow/server/issues/962)).
Such a run now binds the contract of the worker that completes its first
workflow task, once, in the same transaction. Before that, an update returns a
retryable `409 contract_pending` and nothing is recorded. A contract captured
at start is never replaced.

## Sticky execution and history suffixes

Native now follows PHP Server's sticky execution contract and advertises
`sticky_execution` ([#1017](https://github.com/durable-workflow/server/issues/1017)).
A completion's `sticky_cache` claim records the run's sticky worker, and each
workflow claim reports `sticky_replay_mode`. A completion that claims sticky
execution from a worker whose registration does not support it is now refused
with 409, as PHP Server refuses it; native used to ignore the field.

Workers that also list `sticky_history_suffix` receive only the history events
after the boundary they reported, instead of the full history on every task.
With PHP SDK support (durable-workflow/sdk-php#384), a 26-task workflow moved
41 KB of history instead of 573 KB. Workers without the capability are
unchanged.

## Retention in the maintenance loop

With the maintenance loop on (the native image default), expired closed runs
are now pruned every minute for every namespace, up to 1,000 per namespace per
minute, whether or not workers are heartbeating. Runs that must be skipped no
longer stall the ones behind them
([#633](https://github.com/durable-workflow/server/issues/633),
[#500](https://github.com/durable-workflow/server/issues/500)).

## Other fixes

- Registering one search attribute no longer refuses other, unregistered keys
  that running workflows upsert; only registered keys are type-checked
  ([#571](https://github.com/durable-workflow/server/issues/571)).
- Activity failure messages over 64 KiB, or holding a NUL, are stored as a
  labelled preview instead of failing with `storage_unavailable` on MySQL and
  MariaDB; history keeps the full message
  ([#1135](https://github.com/durable-workflow/server/issues/1135)).
- A scheduled run that continues as new keeps its schedule origin
  ([#1143](https://github.com/durable-workflow/server/issues/1143)).
- `GET /api/workflows/` (an empty workflow ID) answers 404 instead of 501
  ([#1006](https://github.com/durable-workflow/server/issues/1006)).
- An auth token with leading or trailing whitespace, such as a newline from a
  Secret file, is refused at startup with a message naming the setting
  ([#554](https://github.com/durable-workflow/server/issues/554)).
- The control-plane OpenAPI lists the `promote` build-id action
  ([#521](https://github.com/durable-workflow/server/issues/521)).

## Known limitations

The [3.3.0 known limitations](3.3.0.md#known-limitations) still apply.
No benchmark speedup is claimed beyond the history-size measurement above.
