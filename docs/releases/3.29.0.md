# Durable Workflow Server 3.29.0 (native)

## One leased workflow task per run

A run can have more than one ready workflow task, for example when a signal
arrives while an activity is running and the activity then completes. Before
this release, two workers could lease both tasks at once. Both replayed the
same history and could record the same next command twice, for example two
timers. Cold replay then refused the duplicate (#1282).

A workflow task is now leased only while no other workflow task of the same run
holds an unexpired lease. Every task poll, held-poll wakeup and signed task
offer applies this check, including across Server processes that share one
database. The waiting task stays ready. It is delivered as soon as the other
lease completes or expires, and its history includes the commands the first
task recorded. Pending signals and activity results are still delivered.

Some behavior stays as before:

- An expired lease, or a lease held by a worker that no longer heartbeats, does
  not block the run. The existing lease recovery still applies, and a
  completion for an expired lease is still refused.
- Update tasks keep their separate authority. They neither wait for nor block
  the run's other workflow tasks. Query tasks are unaffected.
- Workflow tasks of different runs are still leased in parallel.
- Histories that already recorded a duplicate command are not changed. Replay
  diagnosis still reports them.

Workers see fewer concurrent workflow tasks for a single busy run, and no
change for runs with one pending task.

## Abandoned activities outlive their run

`schedule_activity` accepts `cancellation_policy: "abandon"` again (#971). It
requires worker protocol 1.20 with a cooperative cancellation claim, and a
finite `schedule_to_close_timeout`. Without the timeout, the completion is
refused with 422 at `commands.N.schedule_to_close_timeout`.

When the run's cooperative cancellation finishes, an abandoned activity is left
running instead of being cancelled. Until it finishes or reaches its original
`schedule_to_close` deadline:

- It can still be claimed if it was not started, and a running attempt can
  heartbeat and renew its lease.
- Its completion or failure is recorded in the closed run's history and never
  resumes the run.
- At the original deadline it times out with `ActivityTimedOut`.

Server checks this permission against the run's history: the `abandon` policy
and deadline in the activity's `ActivityScheduled` event, the cancellation's
request and delivery, and the run's matching `WorkflowCancelled` close. Any
other activity, or a run closed in any other way, keeps the existing
`run_closed`, `run_cancelled` or `run_terminated` refusals.

Three choices in this release:

- A retryable failure after the run's close is retried under the activity's own
  retry policy, still bounded by its `schedule_to_close` deadline, as Core
  does.
- An expired open activity of a cancelled run without that permission, for
  example a row left from before this release, is cancelled without a history
  event. It is no longer selected again by each deadline check.
- A run that completes, fails or continues as new still cancels its abandoned
  activities. Only the cooperative cancellation leaves them running.

Task queue backlog counts do not include abandoned activities of cancelled
runs.

## Other changes

- Concurrency tests cover external payload claims racing retention pruning and
  update admission under a real InnoDB deadlock. A deadlocked update admission
  still answers `503 storage_unavailable`, records nothing, and is admitted
  once when retried with the same `request_id` (#960).
- `DW_HTTP_ACCESS_LOG` is classified as a native-only setting, and the task
  offer and native SQLite documentation are updated (#1321).
- The native SBOM scan runs on a private copy of the image export (#1307).

## Upgrade from 3.28.0

The database schema and worker protocol version are unchanged. For Docker
Compose, replace the published Compose file and start the stack with the new
image. Server verifies the existing schema at startup. For an earlier schema,
follow the [stopped-node upgrade](3.22.0.md#upgrade-from-3210).

Processes that share one database may run 3.28.0 and 3.29.0 side by side during
a rolling upgrade. Only 3.29.0 processes apply the one-lease-per-run check, so
finish the upgrade before you rely on it.
